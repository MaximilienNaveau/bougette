# Étude : Matrix comme couche de sync, d'identité et de chiffrement (alternative au relais maison)

*Recherche du 2026-11-14. Sources primaires uniquement : spec Matrix (dépôt [`matrix-org/matrix-spec`](https://github.com/matrix-org/matrix-spec), commit `7198bf67` du 2026-11-13, version publiée v1.19 du 2026-07-08), [`matrix-org/matrix-rust-sdk`](https://github.com/matrix-org/matrix-rust-sdk) (clone de `main`, commit `ce055208` du 2026-11-14), MSC sur [`matrix-spec-proposals`](https://github.com/matrix-org/matrix-spec-proposals) (statuts relevés via l'API GitHub), dépôts des homeservers, [fdroiddata](https://gitlab.com/fdroid/fdroiddata) et [nixpkgs](https://github.com/NixOS/nixpkgs) (`master` du jour). « non vérifié » = je n'ai pas pu le confirmer sur une source primaire.*

Contexte : stack n°1 de [`cross-platform-local-first-sync.md`](cross-platform-local-first-sync.md) (§1, §5, §6, §7.4, §8, §10, §11). Question : Matrix peut-il remplacer le relais axum, la gestion d'identité et d'appartenance, et le chiffrement E2E, en gardant notre fusion (HLC + LWW par champ, partie double) au-dessus ?

---

## 1. Verdict

**Adéquation partielle.** Matrix couvre très bien ce qui est le plus risqué à écrire soi-même (identité, appareils, distribution de clés de groupe, sauvegarde des clés, partage de l'historique aux nouveaux membres, file d'envoi hors ligne, serveur auto-hébergeable en Rust sous Apache-2.0), avec un SDK Rust Apache-2.0 utilisé en production. Mais il **ne remplace pas** notre couche de données, et le mapping proposé doit être corrigé sur trois points :

1. **Les state events ne sont pas chiffrés** (MSC3414 et MSC4362 encore ouvertes). Les réglages du budget doivent donc être des événements *message-like* chiffrés, traités en LWW par notre code, et non des state events.
2. **Les power levels ne voient que `m.room.encrypted`** dans un salon chiffré. La lecture seule (personne ne peut rien envoyer) marche ; des droits **par type d'événement** (« peut saisir des dépenses mais pas modifier les règles ») ne sont pas applicables par le serveur et restent à notre charge côté client, exactement comme dans la stack n°1.
3. **L'historique long coûte cher** à un nouvel appareil : pagination de tout le salon (≤ 1000 événements par requête sur Synapse) et import de nombreuses sessions Megolm depuis la sauvegarde. Il faut de toute façon des snapshots chiffrés, que Matrix ne fournit pas.

S'y ajoute un risque propre aux données financières : un seul événement **indéchiffrable** (« UTD ») = une transaction manquante = un solde faux. Le taux d'UTD en pratique est **non vérifié**.

**Recommandation** : ne pas basculer la stack n°1 sur Matrix maintenant. Garder le trait `Transport` (§10.10 de l'étude principale) et faire un **prototype jetable d'une à deux semaines** d'un `MatrixTransport` (matrix-sdk + Tuwunel) pour mesurer les points ci-dessus (§10). Si le prototype passe, Matrix devient le transport et le système de clés par défaut, et nous économisons le relais et la crypto de groupe. Sinon, on garde le relais maison et on réutilise **vodozemac** (pas le protocole Matrix) pour la crypto.

## 3. Chiffrement : ce que Matrix chiffre et ne chiffre pas

- **Événements message-like custom : chiffrés.** Un événement Megolm a pour type extérieur `m.room.encrypted` ; le texte clair `{type, content, room_id}` (donc **notre type** `org.example.budget.transaction`) est dans le chiffré ([spec `m.megolm.v1.aes-sha2`](https://spec.matrix.org/v1.19/client-server-api/#mmegolmv1aes-sha2)). Le serveur voit l'expéditeur, l'appareil, l'heure, la taille et le salon ([spec, événements de salon](https://spec.matrix.org/v1.19/client-server-api/#room-event-format)).
- **State events : non chiffrés aujourd'hui.** [MSC3414](https://github.com/matrix-org/matrix-spec-proposals/pull/3414) (« [WIP] Encrypted state events », ouverte depuis 2021, `needs-implementation`) et son successeur simplifié [MSC4362](https://github.com/matrix-org/matrix-spec-proposals/pull/4362) (ouverte, `needs-implementation`, dernière mise à jour 2026-09-05). MSC4362 : « Currently, all state events are unencrypted » ; elle chiffre le contenu de l'état non critique mais **pas son type** (packé dans `state_key = "{type}:{state_key}"`) et exclut `m.room.create`, `member`, `join_rules`, `power_levels`, `history_visibility`… Elle dépend de MSC4268 ; un état envoyé avant l'arrivée d'un membre lui reste illisible sans MSC4268 ([texte MSC4362](https://github.com/matrix-org/matrix-spec-proposals/blob/a67c5aa7d08fa5bc8b3cba815141d4eed2c8c454/proposals/4362-simplified-encrypted-state.md)). Le SDK l'implémente derrière `experimental-encrypted-state-events` ([`Cargo.toml`](https://github.com/matrix-org/matrix-rust-sdk/blob/main/crates/matrix-sdk/Cargo.toml)). **Conséquence** : tout réglage de budget mis en state (nom, devise, règles de redistribution, catégories) est lisible par l'admin du serveur. Le nom du salon (`m.room.name`) aussi : il faut un nom neutre.
- **Historique pour un nouveau membre : spécifié depuis v1.19.** [MSC3061](https://github.com/matrix-org/matrix-spec-proposals/pull/3061) a été **rejetée** ; elle est remplacée par [MSC4268](https://github.com/matrix-org/matrix-spec-proposals/pull/4268) (fusionnée le 2026-04-08), entrée dans la spec v1.19 ([changelog v1.19](https://spec.matrix.org/v1.19/changelog/v1.19/)). Fonctionnement : avant d'inviter Bob, Alice construit un `RoomKeyBundle` des sessions « shareable » (créées pendant une `history_visibility` `shared` ou `world_readable`), le chiffre et l'uploade comme une pièce jointe, puis l'envoie **uniquement aux appareils cross-signés** de Bob. Bob « MUST remember who he received the keys from » ([spec, Sharing keys between users](https://spec.matrix.org/v1.19/client-server-api/#sharing-keys-between-users)). Le SDK l'active **par défaut** depuis 0.17 (`with_enable_share_history_on_invite`) ([CHANGELOG](https://github.com/matrix-org/matrix-rust-sdk/blob/main/crates/matrix-sdk/CHANGELOG.md)). **Limites** : l'invitant ne partage que les sessions qu'il possède (il doit d'abord tout télécharger depuis sa sauvegarde) ; le bundle est un média que le serveur peut expirer ; une période passée en `joined` crée un trou définitif ([spec](https://spec.matrix.org/v1.19/client-server-api/#construction-and-sharing-of-the-key-bundle)). **Pour nous** : créer chaque salon budget en `history_visibility: shared` et ne jamais le changer.
- **Sauvegarde de clés et clé de récupération** : sauvegarde serveur `m.megolm_backup.v1.curve25519-aes-sha2` ([spec](https://spec.matrix.org/v1.19/client-server-api/#server-side-key-backups)). Côté SDK, le module `encryption::recovery` unifie secret storage et backup (`recovery.enable().with_passphrase(...)` renvoie une clé de récupération), avec `auto_enable_cross_signing` et `auto_enable_backups` ([`recovery/mod.rs`](https://github.com/matrix-org/matrix-rust-sdk/blob/main/crates/matrix-sdk/src/encryption/recovery/mod.rs)). La sauvegarde authentifiée ([MSC4048](https://github.com/matrix-org/matrix-spec-proposals/pull/4048)) est encore ouverte.
- **Vérification d'appareils** : SAS emoji et QR ([spec](https://spec.matrix.org/v1.19/client-server-api/#device-verification)). [MSC4153](https://github.com/matrix-org/matrix-spec-proposals/pull/4153) « Exclude non-cross-signed devices » est fusionnée : un appareil non vérifié ne reçoit plus les clés. **Conséquence UX** : chaque nouvel appareil doit être vérifié (par un autre appareil ou par la clé de récupération), sinon il ne lira rien de neuf.
- **« Unable to decrypt »** : le SDK expose un `UtdHookManager` dédié au suivi de ces événements ([`unable_to_decrypt_hook.rs`](https://github.com/matrix-org/matrix-rust-sdk/blob/main/crates/matrix-sdk-ui/src/unable_to_decrypt_hook.rs)), plus un « redecryptor » qui réessaie quand une clé arrive ([`event_cache/redecryptor.rs`](https://github.com/matrix-org/matrix-rust-sdk/blob/main/crates/matrix-sdk/src/event_cache/redecryptor.rs)). Fréquence réelle dans Element X : **non vérifié** (aucune donnée primaire chiffrée trouvée).

## 4. Permissions

- **`events` dans `m.room.power_levels`** : « If an event type is specified in `events`, then the user must have at least the level specified in order to send that event » ; sinon `events_default` (0) pour les messages, `state_default` (50) pour l'état ([spec `m.room.power_levels`](https://spec.matrix.org/v1.19/client-server-api/#mroompower_levels)). **Mais** dans un salon chiffré, le type contrôlé par le serveur est `m.room.encrypted` (§3). On peut donc régler « peut écrire » ou « ne peut rien écrire », pas « peut écrire des transactions mais pas des réglages ». C'est une déduction de la spec ; MSC4362 ne traite pas des power levels (**non vérifié** qu'une MSC le fasse).
- **Lecture seule** : `events_default: 50` (ou `events["m.room.encrypted"]: 50`), membres lecteurs à 0, écrivains à 50. Le lecteur reçoit quand même les clés Megolm (il est membre), comme dans la stack n°1 (« la clé est fournie, mais aucun droit de push », §7.4).
- **Redaction des événements d'autrui** : « The power level required to redact an event sent by another user is *additionally* governed by `redact` » (défaut 50) ([spec](https://spec.matrix.org/v1.19/client-server-api/#mroompower_levels)). **Piège** : côté serveur, une redaction s'applique aussi si « the domain of the redaction event's sender matches that of the original event's sender » ([room v12, Handling redactions](https://spec.matrix.org/v1.19/rooms/v12/#handling-redactions)). Sur **un seul homeserver familial**, tout le monde a le même domaine. La parade est de fixer `events["m.room.redaction"]` au-dessus du niveau des écrivains, car la règle d'auth porte, elle, sur ce type ([room v12, auth rules](https://spec.matrix.org/v1.19/rooms/v12/#authorization-rules)). Notre modèle étant en ajout seul (§6), on n'a de toute façon pas besoin de redactions.
- **Room v12** : les créateurs ont un niveau de pouvoir infini et ne peuvent pas figurer dans `users` ([schéma](https://github.com/matrix-org/matrix-spec/blob/main/data/event-schemas/schema/m.room.power_levels.yaml)). Le créateur d'un budget en reste donc admin à vie.
- **Ce que le serveur peut faire** : il lit tout l'état (membres, power levels, nom) ; il signe les événements de ses utilisateurs ([spec fédération, signatures](https://spec.matrix.org/v1.19/server-server-api/#authentication)) ; un admin peut purger l'historique ([Synapse purge_history](https://github.com/element-hq/synapse/blob/develop/docs/admin_api/purge_history_api.md)). Le contenu Megolm reste authentifié par les clés d'appareil de l'expéditeur, mais l'**appartenance et les rôles sont « trust the server »**. Notre client doit donc revérifier le rôle de l'auteur de chaque événement à partir de l'état du salon, sans protection contre un serveur malveillant qui forgerait un `power_levels` (**non vérifié** : pas d'analyse détaillée de ce scénario).

## 5. Ordre et conflits

- Le DAG (`prev_events`) donne un **ordre partiel** ([spec PDUs](https://spec.matrix.org/v1.19/server-server-api/#pdus)) ; `/messages` ordonne « according to the arrival time of the event on the homeserver », ce qui peut contredire l'ordre du graphe ([spec Syncing](https://spec.matrix.org/v1.19/client-server-api/#syncing)). `origin_server_ts` est l'heure de **réception par le serveur** ([schéma](https://github.com/matrix-org/matrix-spec/blob/main/data/event-schemas/schema/core-event-schema/sync_room_event.yaml)).
- **Deux appareils hors ligne** : leurs événements restent dans les send queues locales et arrivent à la reconnexion, ordonnés par **heure d'arrivée**, pas par heure de saisie. Un appareil resté hors ligne une semaine « écrase » donc des modifications plus récentes si l'on applique LWW sur l'ordre Matrix. **Il faut garder notre HLC dans le contenu chiffré** et faire LWW sur l'HLC, comme prévu.
- La **state resolution v2** ne concerne que les state events (et n'utilise ni notre HLC ni notre sémantique de champ). Elle ne fusionne pas des champs ; elle choisit un événement d'état gagnant par `(type, state_key)`. Inutilisable pour nos données, d'autant que l'état n'est pas chiffré.
- **Ce que Matrix nous donne en plus** : un id unique par événement (`event_id`) pour la déduplication, un transport fiable et ordonné par appareil (send queue), et l'authenticité de l'expéditeur. **Ce qu'il ne donne pas** : le Merkle et la détection de « trous ». Un événement présent mais **indéchiffrable** doit être traité comme un trou bloquant (budget marqué « incomplet »), sinon un solde est faux sans que personne le voie.

## 6. Croissance de l'historique et performances

- **Rattrapage d'un nouvel appareil** : `/messages` renvoie 10 événements par défaut ([spec](https://spec.matrix.org/v1.19/client-server-api/#get_matrixclientv3roomsroomidmessages)) et Synapse plafonne `limit` à **1000** (`MAX_LIMIT`, [`streams/config.py`](https://github.com/element-hq/synapse/blob/develop/synapse/streams/config.py)). Un budget de 100 000 événements demande donc au moins 100 allers-retours, puis le déchiffrement de chaque événement. Les plafonds de Conduit, Tuwunel et continuwuity sont **non vérifiés**.
- **Clés** : une session Megolm tourne par défaut toutes les **100** messages ou **7 jours** ([`m.room.encryption`](https://spec.matrix.org/v1.19/client-server-api/#mroomencryption)), par expéditeur. Le nombre de sessions à télécharger depuis la sauvegarde croît avec l'historique et le nombre d'écrivains (coût réel **non vérifié**).
- **Sliding Sync MSC4186** : MSC fusionnée le 2026-06-29, avec le label `spec-pr-missing`, donc pas encore dans la spec ([PR](https://github.com/matrix-org/matrix-spec-proposals/pull/4186)). Elle n'est requise que pour `matrix-sdk-ui` ; `Client::sync` (v2) suffit pour nous. Support serveur : **Synapse**, natif et activé par défaut depuis **1.114.0** (2024-09-02) ([CHANGES-2024](https://github.com/element-hq/synapse/blob/develop/docs/changelogs/CHANGES-2024.md)) ; **Conduit** (`sync_events_v5_route`, `org.matrix.simplified_msc3575` annoncé, [`main.rs`](https://gitlab.com/famedly/conduit/-/blob/next/conduit/src/main.rs), [`unversioned.rs`](https://gitlab.com/famedly/conduit/-/blob/next/conduit/src/api/client_server/unversioned.rs)) ; **Tuwunel** ([`sync/v5.rs`](https://github.com/matrix-construct/tuwunel/blob/main/src/api/client/sync/v5.rs)) ; **continuwuity** ([`sync/v5.rs`](https://github.com/continuwuity/continuwuity/blob/main/src/api/client/sync/v5.rs)). La complétude de ces implémentations est **non vérifiée**.
- **Compaction** : Matrix n'en fournit pas. Options :
  1. **Événement snapshot** périodique (comme [Matrix-CRDT](https://github.com/YousefED/Matrix-CRDT), qui envoie un `matrix-crdt.doc_snapshot` toutes les 30 mises à jour avec `last_event_id`). Un événement est limité à **64 KiB** ([spec Size limits](https://spec.matrix.org/v1.19/client-server-api/#size-limits)), donc un snapshot de budget doit être une **pièce jointe chiffrée** (média) référencée par un petit événement. Le nouvel appareil lit le dernier snapshot puis pagine **vers l'arrière seulement jusqu'à lui**.
  2. **Upgrade de salon** (`m.room.tombstone` + `predecessor`, [spec Room upgrades](https://spec.matrix.org/v1.19/client-server-api/#room-upgrades)) : un salon neuf démarre au snapshot. Il faut réinviter et revérifier, perdre l'`event_id` de continuité, et les clés de l'ancien salon restent utiles pour l'audit. C'est lourd pour une famille ; à réserver à une « clôture d'exercice » annuelle.
  3. **Redaction** : elle supprime le contenu mais pas l'événement (squelette conservé, [règles v11](https://spec.matrix.org/v1.19/rooms/v11/#redactions)). Elle n'allège donc pas la pagination et ne sert pas à compacter.

### 7.1 Petit serveur à la maison

- **Consommation de ressources** : aucun des quatre projets ne publie de chiffres RAM ou CPU mesurés pour une petite machine dans les sources lues (README, docs Tuwunel). Les seuls repères sont qualitatifs : Conduit vise le Raspberry Pi familial ([README](https://gitlab.com/famedly/conduit/-/blob/next/README.md)), et Synapse exige PostgreSQL en production ([installation.md](https://github.com/element-hq/synapse/blob/develop/docs/setup/installation.md)), soit un service de plus à faire tourner. Les chiffres sont donc **non vérifiés** ; c'est une mesure à faire dans le prototype (§14).
- **Comparaison avec le relais maison** : sur une machine domestique, un homeserver Rust sans fédération (Tuwunel, continuwuity, Conduit : un binaire + RocksDB) reste un service unique, comme le relais axum de la stack n°1. Mais il embarque bien plus de surface (médias, comptes, appareils, push, fédération désactivée mais présente). Synapse + PostgreSQL est l'option la plus lourde pour une petite machine (interprétation, chiffres **non vérifiés**).
- **Accessibilité** : un homeserver doit être joignable par les téléphones hors du réseau local (TLS, nom de domaine, `.well-known` ou port 8448 seulement si fédération). Le relais maison a exactement le même besoin. Matrix n'ajoute rien ici tant que la fédération est coupée.

### 7.2 Service communautaire chez un hébergeur CHATONS

L'utilisateur dispose aussi d'un serveur chez datcat.fr, membre du collectif CHATONS. Ce qui, dans la [charte CHATONS](https://www.chatons.org/charte), s'applique à un homeserver ou à notre relais proposé comme service ouvert à d'autres :

- **Logiciels libres exclusivement** : le membre « s’engage à utiliser exclusivement des logiciels soumis à des licences libres », et « s'il modifie le code source des logiciels utilisés, à rendre publiques ces modifications ». Synapse (AGPL), les serveurs Rust (Apache-2.0) et notre relais (`MIT OR Apache-2.0`) conviennent tous. Avec l'AGPL de Synapse, l'obligation de publier les modifications existe aussi par la licence elle-même.
- **Données** : pas d'« exploitation commerciale des données ou métadonnées des hébergé·es », aucun droit de propriété sur « contenus, données et métadonnées », et « un chiffrement fort des données » autant que possible. **Un service où l'hébergeur ne lit pas le contenu (E2EE) s'accorde bien avec ces engagements.** Les deux options le permettent pour les transactions ; avec Matrix, l'état du salon (membres, rôles, nom) et les métadonnées restent lisibles par l'hébergeur (§3, §10.2), et le relais maison expose `budget_id`, `hlc`, `author` et taille (§7.4 de l'étude principale).
- **Transparence** : publier l'infrastructure technique (« distribution et logiciels utilisés »), des **CGU** avec une clause de données personnelles, et la **politique de sauvegarde**. Pour un relais ou un homeserver de budgets chiffrés, la politique de sauvegarde doit dire clairement que l'hébergeur ne peut pas restaurer les **clés** des utilisateurs (clé de récupération, phrase de récupération).
- **Neutralité** : ne transmettre des données personnelles qu'après une « requête légale ». Avec l'E2EE, seules les métadonnées seraient transmissibles.
- **Pas de régie publicitaire.**

Tous les éléments ci-dessus viennent de la charte ([chatons.org/charte](https://www.chatons.org/charte), consultée le 2026-11-14). L'annuaire des services de chatons.org propose « Matrix » et « Synapse » parmi ses filtres de logiciels ([recherche par service](https://www.chatons.org/search/by-service)), donc Matrix est déjà un type de service connu du collectif ; je n'ai pas pu lister les membres qui l'offrent (**non vérifié**), ni vérifier si datcat.fr propose déjà Matrix.

**Conséquence pour le choix** : du point de vue d'un CHATON, **un homeserver Matrix est un service générique** (messagerie, utile au-delà de notre app) qu'un membre peut déjà proposer ou ajouter à son catalogue, alors qu'un **relais spécifique à notre app** est un service de niche que l'hébergeur devrait accepter d'opérer et de mettre à jour pour une seule application. C'est un argument réel pour Matrix (ou pour un relais très simple, sans état métier, facile à empaqueter et documenter : module NixOS, paquet Debian). En contrepartie, un homeserver ouvert à des inscriptions publiques fait de notre app un client parmi d'autres sur ce serveur, avec des comptes partagés avec le chat (interprétation, **non vérifiée** auprès d'un CHATON).

## 8. F-Droid et nixpkgs

- **Element X Android est dans le dépôt principal F-Droid**, avec des builds **reproductibles** : `binary:` pointant vers l'APK signé de l'amont, `AllowedAPKSigningKeys`, un bloc par ABI, `ndk: r28c`, version 26.09.1 ([`io.element.android.x.yml`](https://gitlab.com/fdroid/fdroiddata/-/blob/master/metadata/io.element.android.x.yml)). La recette supprime Firebase (`rm: libraries/pushproviders/firebase`, `sed '/gms/d'`).
- **Mais F-Droid ne compile pas le SDK Rust pour Element X** : la recette n'installe ni rustup ni cargo. Le SDK arrive sous forme d'**AAR précompilé depuis Maven Central** (`org.matrix.rustcomponents:sdk-android`, [libs.versions.toml](https://github.com/element-hq/element-x-android/blob/develop/gradle/libs.versions.toml)), ce que l'Inclusion Policy tolère (« provided in a trusted Maven repo », [Inclusion Policy](https://f-droid.org/docs/Inclusion_Policy/)). Ce précédent ne nous aide donc pas : notre app compilera `matrix-sdk` **depuis les sources** dans notre crate via cargokit, comme pour le reste de `budget-core` (§11.4 de l'étude principale). Cela ajoute `aws-lc-sys` (C/CMake) et SQLite à la recette. Aucune recette fdroiddata qui compile `matrix-sdk` depuis les sources n'a été trouvée (**non vérifié** de façon exhaustive).
- **Flutter + matrix-rust-sdk** : aucune app publiée trouvée. Seulement des expériences (ex. [kushalmahapatro/matrix-frb](https://github.com/kushalmahapatro/matrix-frb), 2 ★, sans licence).
- **SDK Dart (famedly/matrix-dart-sdk)** : **AGPL-3.0** depuis le premier commit ([LICENSE](https://github.com/famedly/matrix-dart-sdk/blob/main/LICENSE)), et sa crypto [`famedly/dart-vodozemac`](https://github.com/famedly/dart-vodozemac) est aussi **AGPL-3.0**. Lié dans le client, il imposerait l'AGPL à l'app : **exclu** par la contrainte `MIT OR Apache-2.0`. FluffyChat (AGPL-3.0) l'utilise ([fdroiddata](https://gitlab.com/fdroid/fdroiddata/-/blob/master/metadata/chat.fluffy.fluffychat.yml)).
- **nixpkgs** : iamb (`rustPlatform.buildRustPackage`, `cargoHash`, `sqlite`, [package.nix](https://github.com/NixOS/nixpkgs/blob/master/pkgs/by-name/ia/iamb/package.nix)) et Fractal (meson + `fetchCargoVendor`, `openssl`, `sqlite`, [package.nix](https://github.com/NixOS/nixpkgs/blob/master/pkgs/by-name/fr/fractal/package.nix)) empaquettent déjà des apps `matrix-sdk` sans difficulté particulière. Pour nous, rien de plus que §11.5 de l'étude principale : un `Cargo.lock` plus gros et un `cargoHash` qui change à chaque montée de version.

## 10. Inconvénients

1. **Comptes et UX familiale** : chaque membre a besoin d'un compte `@nom:serveur`. On peut limiter l'inscription par jeton (`m.login.registration_token`, [spec](https://spec.matrix.org/v1.19/client-server-api/#token-authenticated-registration)) et le cacher dans un QR d'invitation. Matrix 2.0 pousse l'authentification OAuth 2.0 ([MSC3861](https://github.com/matrix-org/matrix-spec-proposals/pull/3861), fusionnée), qui demande un service d'authentification en plus pour Synapse (MAS) ; le support natif dans Tuwunel et continuwuity est **non vérifié**. S'ajoutent la vérification de chaque nouvel appareil (MSC4153) et la clé de récupération. La stack n°1 aurait aussi une phrase de récupération, mais pas de comptes serveur ni d'étape de vérification.
2. **Métadonnées** : le serveur voit les membres, les rôles, le nom du salon, l'état, l'heure et la taille de chaque transaction (une transaction ≈ un événement). C'est comparable à la stack n°1 (`budget_id`, `hlc`, `author`, taille, §7.4), plus l'état en clair. **Désactiver la fédération** sur le serveur familial évite de diffuser ces métadonnées à d'autres serveurs (option de config par serveur **non vérifiée** pour chacun).
3. **Dépendance à Element** : le SDK est « sponsored and maintained by Element » ([README](https://github.com/matrix-org/matrix-rust-sdk/blob/main/README.md)) ; Element a déjà relicencié Synapse en AGPL faute de rentabilité ([blog](https://element.io/blog/element-to-adopt-agplv3/)). Un relicenciement futur du SDK (aujourd'hui sous l'organisation matrix-org) est **non vérifié** et spéculatif, mais Apache-2.0 permettrait de forker la dernière version. Les priorités du SDK suivent Element X (chat, appels, Sliding Sync), pas le stockage de données.
4. **Exploitation** : un homeserver complet (fédération, médias, push, sauvegardes, mises à jour de sécurité) contre un relais de quelques centaines de lignes. Les serveurs Rust sont légers, mais restent un logiciel bien plus large que notre besoin.
5. **Notifications sans Google** : Element X embarque le connecteur UnifiedPush (`org.unifiedpush.android:connector:3.3.5`, [libs.versions.toml](https://github.com/element-hq/element-x-android/blob/develop/gradle/libs.versions.toml)). Avec Matrix, il faut une passerelle push en plus ([spec Push Gateway](https://spec.matrix.org/v1.19/push-gateway-api/)). Pour une app budget, une sync à l'ouverture suffit probablement : pas de push en v1.
6. **Taille et build** : SDK volumineux (§2), `aws-lc-sys` en C, MSRV récente (1.96), API 0.x qui casse 3 à 4 fois par an.
7. **Correction financière** : UTD = trou silencieux ; ordre par arrivée et non par saisie ; pas de Merkle. Il faut notre propre contrôle d'intégrité (compteur ou Merkle par auteur dans le contenu chiffré).

## 12. Risques

| Risque | Gravité | Parade |
|---|---|---|
| Événement indéchiffrable → solde faux silencieux | **haute** | Budget marqué « incomplet » tant qu'un événement est UTD ; compteur par auteur (séquence) dans le contenu pour détecter les trous ; tests de bout en bout multi-appareils |
| Réglages ou structure lisibles par le serveur (state, spaces, nom de salon) | moyenne | Tout en message-like chiffré ; noms neutres ; surveiller MSC4362 |
| Rôles fins non applicables par le serveur | moyenne | Vérification côté client à l'état du salon (comme la stack n°1) ; ne pas promettre de rôles serveur |
| API 0.x qui casse souvent | moyenne | Isoler Matrix derrière `Transport` ; épingler la version ; une montée par trimestre |
| Coût du rattrapage (10k–100k événements) | moyenne | Snapshot chiffré en média + pagination limitée ; clôture annuelle par upgrade de salon |
| Partage d'historique incomplet (invitant sans toutes les clés, appareil non cross-signé) | moyenne | `shared` dès la création ; l'invitant télécharge sa sauvegarde ; le snapshot contient l'état courant de toute façon |
| UX comptes et vérification trop lourde pour la famille | moyenne | Jeton d'inscription dans un QR ; vérification par QR ; tests utilisateurs |
| Build F-Droid de `matrix-sdk` depuis les sources (aws-lc-sys, taille) | moyenne | Prototype de recette tôt ; voir si le backend `ring` est possible (**non vérifié**) |
| Dépendance à la feuille de route d'Element | faible à moyenne | Apache-2.0 forkable ; Transport abstrait |
| Serveur malveillant qui forge appartenance ou rôles | faible (serveur familial) | Vérifications client ; à documenter dans le modèle de menace |

## 14. Prochaine étape recommandée : prototype jetable (1 à 2 semaines)

Un crate Rust `matrix-transport-spike` **hors du dépôt principal**, CLI uniquement (pas de Flutter), contre un **Tuwunel** lancé par `services.matrix-tuwunel` dans une VM NixOS. Il doit tester :

1. **Mapping** : créer un space et deux salons `org.example.budget`, `history_visibility: shared`, power levels « lecteur » (`events_default` 50, `m.room.redaction` 100) ; vérifier côté serveur qu'un lecteur ne peut **ni envoyer ni redacter**, et qu'un écrivain ne peut pas redacter l'événement d'un autre.
2. **Hors ligne** : deux clients (A, B) éditent le même champ hors ligne avec des HLC croisés, se reconnectent dans l'ordre inverse ; vérifier que notre LWW-HLC converge malgré l'ordre d'arrivée Matrix.
3. **Nouveau membre** : C invité après 5 000 transactions ; mesurer le temps et le nombre de requêtes pour tout déchiffrer (MSC4268 + pagination), puis la même chose avec un snapshot chiffré en média.
4. **Appareil perdu** : A se reconnecte sur un appareil neuf avec la seule clé de récupération ; compter les UTD restants.
5. **Échelle** : 100 000 événements dans un salon ; temps de rattrapage, taille des stores SQLite du SDK ; **RAM et CPU de Tuwunel** sur la machine domestique de l'utilisateur, comparés au relais axum.
